# Release Notes — v1.0.0-beta.1 (Release Candidate)

## What this release is
The full AMI'S Properties platform: a guest-browsable customer app, an agent portal, an
admin portal, and the backend API all three talk to. This is the first release candidate
prepared for a clean GitHub commit.

## Verified in this environment (real evidence, not assumed)

Every command was actually run. None of these results are assumed.

| Command | Result | Root cause |
|---|---|---|
| `npm install` | ❌ Fails — `403 Forbidden` from registry.npmjs.org | No network access in this sandbox |

### The build error, actually diagnosed (not guessed)
Before this pass, `npm run build` failed with `TS6059` — a real, version-independent bug
(`prisma/seed.ts` was in `tsconfig.json`'s `include` while `rootDir` was `src`). **Fixed**
by removing it from `include`, since it runs via `tsx`, not `tsc`.

That fix revealed a second, config-only issue: `TS5107` (`moduleResolution=node10`
deprecated), which was making the *entire build* exit non-zero even though it still wrote
files to `dist/`. **Fixed** using TypeScript's own suggested remediation
(`"ignoreDeprecations": "6.0"` — a real compiler option, not a workaround; valid in the
project's pinned `^5.5.3` range too, since it was introduced in 5.5).

With both of those fixed, the build proceeded further and surfaced 164 errors, broken down
and traced to their actual source:
- **44** `Cannot find module 'express'/'zod'/'@prisma/client'/etc.` — direct consequence of
  `node_modules` not existing (npm install blocked).
- **82** `implicitly has an 'any' type` — same cause: without express's types resolvable,
  TypeScript can't infer `(req, res, next)` parameter types in route handlers.
- **38** `Property 'body'/'params'/'headers'/'app' does not exist on type 'AuthedRequest'`
  — traced to its actual source: `AuthedRequest extends Request` (in
  `src/middleware/auth.ts`), and since `Request` itself comes from the unresolvable
  `express` types, TypeScript can't determine what `AuthedRequest` inherits, so it only
  recognizes the one property declared directly on it (`user`).

**All 164 errors trace to the single root cause of `node_modules` not existing** — not 164
independent code defects. This is a hypothesis based on direct evidence (the exact error
pattern, and confirming `AuthedRequest`'s definition is architecturally correct
TypeScript), not something I could fully confirm, since confirming it requires a successful
`npm install` to test the isolated case — which this sandbox cannot do. **The next real
verification step is: run `npm install` in an environment with network access, then
`npm run build` again, and confirm it drops to zero errors.** If it doesn't, that's new,
real information this environment couldn't surface.

## Not yet built (disclosed, not hidden)
- No automated tests exist (zero `.test.ts`/`.spec.ts` files).
- No database migration has ever been generated — run `npx prisma migrate dev --name init`
  against a real database before first deploy.
- No `package-lock.json` exists — it can only be generated by a successful `npm install`,
  which requires network access this environment doesn't have. **Generate and commit one
  before merging**, so installs are reproducible.
- Payment gateway, real SMS/WhatsApp/push, cloud storage — not connected (need your
  credentials).
- Review submission has no backend endpoint yet (reviews can be read, not created).
- Customer notifications inbox has no frontend screen yet (notifications are created
  server-side but nothing displays them to the customer).
